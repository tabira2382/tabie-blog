全部にテストを書くのではなく、**壊れたときに顧客の業務に直接影響する部分から**テストを入れ、段階的に広げます。マーケティングデータ分析プラットフォームでは、ビジネスロジックとエラーハンドリングに絞ってテストを整備し、品質を保ちながら**新機能を1ヶ月でリリース**しました。

## 状況

機能を追加するたびに、別の画面や既存の機能が壊れます。リリース前の手動確認に時間がかかり、それでも漏れが出ます。テストを書こうにも、どこから手を付けるべきか決まっていません。

## 一番まずい点と、その理由

**「どこが壊れると困るか」が決まっていないことです。**

テストがないこと自体より、守るべき場所の優先順位がないことが問題です。優先順位がないまま「テストを書こう」とすると、書きやすい箇所ばかりが増えて管理コストが膨らみ、肝心の部分は守られないままになります。

## 対処方針と判断の理由

**壊れたときの影響が大きい順にテストを入れ、段階的に広げます。**

1. まず、壊れると顧客の業務に直接影響する部分（計算・集計などのビジネスロジック、エラーハンドリング）に単体テストを入れる
2. 次に、画面とデータのつなぎ目など、デグレが実際に起きている箇所に統合テストを足す
3. 主要な操作の流れだけを E2E テストで守り、CI で自動実行してリリース前の手動確認を減らす

あわせて、機能ごとにコードを分ける設計（Feature-based）にして、変更の影響が他の機能に広がらないようにします。

### テストを入れる順番

| 段階 | 守る対象 | テストの種類 | このブログでの例 |
|---|---|---|---|
| 1 | 壊れると顧客の業務に直接影響する処理（ビジネスロジック、エラーハンドリング） | 単体テスト（Vitest） | 記事の取得・タグでの絞り込み（`posts.test.ts`）、MDX の変換（`mdx.test.ts`） |
| 2 | 画面の表示（データが正しく画面に出るか） | 統合テスト（Testing Library） | 記事カードにタイトル・日付・タグ・リンクが出るか（`PostCard.test.tsx`） |
| 3 | 主要な操作の流れ | E2E テスト（Playwright） | 記事一覧から詳細への移動、タグでの絞り込み（`e2e/blog.spec.ts`） |

実際の案件では、リリースまでの時間が限られていたため、まず段階1に絞りました。

| | 内容 |
|---|---|
| メリット | 少ない工数で、一番守りたい部分から品質を担保できる。開発スピードを落とさずに始められる |
| デメリット | テストのない部分が残るため、そこでのデグレは防げない |
| デメリットへの対処 | デグレが起きた箇所は、その都度テストを足す対象に加える。影響範囲を機能単位に閉じる設計で、壊れる範囲自体を狭くする |

選ばなかった選択肢は次の2つです。

- **全部にテストを書く**：書くにも保守するにも工数がかかり、開発スピードとの両立が難しい
- **E2E テスト中心にする**：実行に時間がかかり、壊れやすいので、最初の一手としては負担が大きい

## 現場での実践と結果

### マーケティングデータ分析プラットフォーム

- 1ヶ月でのリリースを優先する方針の中で、テストをビジネスロジックとエラーハンドリングに絞り、Feature-based アーキテクチャを導入した
- 品質と開発スピードのバランスを保ったまま、**新機能を1ヶ月でリリースした**
- その後、方針が入っていない他の機能でデグレが頻発していることが課題として見えてきたため、この方針をチーム外にも横展開している

### このブログ（個人開発）

- 現場に持ち帰れるテスト設計を探るため、単体（Vitest）・統合（Testing Library）・E2E（Playwright）の使い分けを検証した
- GitHub Actions で lint・テスト・ビルド・E2E を自動実行する CI を構築した

| タイミング | 自動で走るもの | 仕組み |
|---|---|---|
| コミット時 | コード整形と lint（Biome）、型チェック、コミットメッセージの形式チェック（commitlint） | Lefthook |
| プッシュ時 | テスト、ビルド | Lefthook |
| プルリクエスト・main への反映時 | lint と型チェック、テスト、ビルド、E2E | GitHub Actions |

手元で早めに気づける検査はコミット・プッシュ時に、時間のかかる E2E は CI に回しています。

## 現場に合わせた調整

- **リリースを急ぐ初期フェーズ**：ビジネスロジックの単体テストだけに絞り、E2E は後回しにする
- **すでにデグレが頻発している現場**：直近でデグレが起きた箇所から優先して統合テストを足す
- **テストの文化がないチーム**：最初は CI で自動実行される仕組みを作るところから始め、書く範囲はチームで議論して決める

どの場合も、いきなり全部を変えるのではなく、チームで優先度を決めて段階的に進めます。
