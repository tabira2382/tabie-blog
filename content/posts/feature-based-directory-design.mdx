機能が増えても壊れにくくするために、**機能単位でコードを分け、変更の影響をその機能の中に閉じ込める**設計にします。マーケティングデータ分析プラットフォームで導入し、このブログ（個人開発）で検証した方針を現場に還元しています。

## 状況

機能を追加するたびに、どこにコードを置くか人によって違い、影響範囲が読めません。ある画面の修正が別の画面を壊します。新しく入ったメンバーが、どこを触ればよいか分かりません。

## 一番まずい点と、その理由

**設計方針がチームで共有されていないことです。**

個々の実装が悪いのではなく、「どこに何を置き、何をどう分けるか」の共通ルールがないため、機能が増えるほどコードが絡み合います。その結果、変更の影響範囲が読めず、デグレや手戻りが増え、機能追加のスピードも落ちていきます。

## 対処方針と判断の理由

**機能単位で分け、変更の影響をその中に閉じ込めます。**

1. **機能単位でディレクトリを分ける（Feature-based）**：機能ごとに状態管理・処理・コンポーネント・ユーティリティをまとめ、他の機能との依存を減らす
2. **ロジックとUIを分ける（Container/Presenter）**：データの取得や加工と見た目を切り分け、それぞれを単独で変更・テストできるようにする
3. **変わりやすい部分を一か所に集める**：権限など仕様変更が多い部分は、改修箇所が一か所で済むようにまとめる

### 構成例（このブログのディレクトリ構成から抜粋）

```text
src/
├── app/                                # ルーティングとメタデータだけ
│   └── (main)/blog/[slug]/page.tsx
├── features/
│   └── blog/                           # 「ブログ」機能に関わるものをここに集める
│       ├── components/
│       │   ├── client/                 # ブラウザで動く部品
│       │   │   ├── PostCard/
│       │   │   │   ├── PostCard.tsx
│       │   │   │   ├── PostCard.test.tsx
│       │   │   │   └── index.ts
│       │   │   └── TableOfContents/
│       │   │       ├── TableOfContentsContainer.tsx
│       │   │       ├── TableOfContentsPresenter.tsx
│       │   │       ├── useTableOfContents.ts
│       │   │       └── index.ts
│       │   └── server/                 # サーバー側で組み立てるページの骨組み
│       │       ├── PostDetailTemplate.tsx
│       │       └── PostListTemplate.tsx
│       ├── lib/                        # 記事の取得・MDX変換などの処理
│       │   ├── posts.ts
│       │   └── posts.test.ts
│       ├── types/
│       └── index.ts                    # 機能の外に公開する処理と型の窓口
├── components/                         # 機能をまたいで使う共通部品
│   ├── layouts/                        # Header、Footer
│   └── ui/                             # button、card など
└── lib/utils.ts
```

| 場所 | 置くもの | ルール |
|---|---|---|
| `app/` | ページの入口（ルーティング、メタデータ） | 記事の取得や表示は features に任せ、ここには書かない |
| `features/機能名/` | その機能の部品・処理・型 | 1つの機能の変更は、このフォルダの中で完結させる |
| `features/機能名/index.ts` | 機能の外に公開する処理と型 | 主な処理はここから公開し、他の場所からはここを経由して使う |
| `features/機能名/lib/` | データの取得・変換などの処理 | 同じ場所にテストを置く（`posts.ts` と `posts.test.ts`） |
| `components/` | 複数の機能で使う共通部品 | 特定の機能の都合を持ち込まない |

実際の案件でも同じ考え方で、機能ごとに `_store`（状態管理）・`_actions`（処理）・`_components`（部品）・`_utils`（補助関数）を置く構成にしました。

### Container/Presenter の分け方（目次コンポーネントの例）

| ファイル | 役割 |
|---|---|
| `useTableOfContents.ts` | 動き：スクロール位置に合わせた見出しの追従、クリックでの移動 |
| `TableOfContentsContainer.tsx` | つなぎ：Hook を呼び出し、結果を Presenter に渡すだけ |
| `TableOfContentsPresenter.tsx` | 見た目：受け取った値で目次を描画するだけ |
| `index.ts` | 外に公開するのは Container だけ |

Container は次のように、Hook の結果を Presenter に渡すだけです。

```tsx
export function TableOfContentsContainer({ toc }: TableOfContentsContainerProps) {
  const { activeId, onClickItem } = useTableOfContents(toc)

  return <TableOfContentsPresenter toc={toc} activeId={activeId} onClickItem={onClickItem} />
}
```

見た目を変えたいときは Presenter だけ、動きを変えたいときは Hook だけを直せばよく、変更の影響が混ざりません。

| | 内容 |
|---|---|
| メリット | 変更の影響範囲が機能の中に限られ、デグレが起きにくい。コードの置き場所が決まり、新しいメンバーも迷わない |
| デメリット | 最初にルールを決めてチームに共有する手間がかかる。機能をまたぐ共通部分の扱いに判断が必要 |
| デメリットへの対処 | 一度に全体を作り直さず、新しく作る機能から適用して横に広げる。共通部分の扱いはチームで議論して決める |

選ばなかった選択肢は次の2つです。

- **種類別のフォルダ構成**（components/、hooks/ などに分ける）：小さいうちは分かりやすいが、機能が増えると1つの修正が複数のフォルダにまたがり、影響範囲が読みにくい
- **大きく作り直す**：リスクが大きく、機能追加を止めることになる

| 観点 | 種類別（components/、hooks/、utils/ …） | 機能別（features/blog/ …） |
|---|---|---|
| 記事カードを直すとき触る場所 | components/、hooks/、utils/、types/ に散らばる | features/blog/ の中だけ |
| 影響範囲の見積もり | フォルダを横断して探す必要がある | 機能フォルダの中を見ればよい |
| 機能を削除・作り直すとき | 各フォルダから関係するファイルを探す | 機能フォルダごと扱える |

## 現場での実践と結果

### マーケティングデータ分析プラットフォーム

- Feature-based アーキテクチャを設計・導入し、変更の影響範囲を機能単位に限定した
- 限られた工数の中でも品質を保ち、新機能を1ヶ月でリリースした
- 他の機能にはまだ方針が入っておらずデグレが起きているため、この方針を横展開している

### このブログ（個人開発）

- 案件の現場で設計方針が共有されていない課題を感じ、いきなり本番で試すのはリスクがあるため、検証環境として個人開発した
- Bulletproof React を参考にした features/ ディレクトリ設計と、Container/Presenter パターンを実践した

### 建物の予約管理システム

- 権限まわりは仕様変更が多いと予想し、認可制御の改修箇所を1ファイルに集約する設計にした

## 現場に合わせた調整

- **立ち上げ直後の小さなプロダクト**：ルールは最小限にとどめ、機能が増えてきた段階で Feature-based に移す
- **すでにコードが大きい現場**：新しく作る機能から適用し、既存の部分は触るタイミングで少しずつ移す
- **複数チームが同じコードを触る現場**：ディレクトリのルールを文書にまとめ、コードレビューで揃える

どの場合も、現場の今の構成を尊重し、チームで議論して無理なく移れる順番を決めます。
