API の仕様ズレは、ツールがないことより「仕様を誰がいつ確定させ、どう共有するか」が決まっていないことで起きます。そこで、**仕様管理ツールと運用フローをセットで**導入します。12名規模のRAGチャットSaaSの開発で実践し、フロント・バック間の仕様ズレと結合時の手戻りを減らしました。

## 状況

API の仕様が口頭やチャットで決まり、最新の仕様がどこにあるか分かりません。フロントとバックで認識がずれたまま実装が進み、結合テストの段階で食い違いが見つかります。

## 一番まずい点と、その理由

**仕様を確定させて共有するプロセスがないことです。**

仕様の置き場所がないだけなら、ツールを入れれば解決します。しかし「誰がいつ仕様を確定させ、変更をどう伝えるか」が決まっていないと、ツールを入れても更新されなくなり、結局チャットに戻ってしまいます。

## 対処方針と判断の理由

**仕様管理ツールと、それを使い続けるための運用フローをセットで入れます。**

1. API の設計書を一か所（API 管理ツール）にまとめ、そこを唯一の正しい仕様とする
2. 仕様の作成・確定・変更の流れと担当を決め、設計書の管理・実行テスト・テストケース作成までを同じツールで一元化する
3. 可能な場合は、仕様（OpenAPI）からフロントの API クライアントを自動生成し、仕様と実装が食い違う余地そのものをなくす

### 設計書から実装までの流れ

| 順番 | 作るもの | 元にするもの |
|---|---|---|
| 1 | API 設計書（管理ツールに一元化） | ユースケースと画面の要件 |
| 2 | バックエンドの実装 | API 設計書 |
| 3 | フロントの API クライアント（OpenAPI から自動生成） | API 設計書 |
| 4 | フロントエンドの実装 | 自動生成した API クライアント |
| 5 | 実行テスト・テストケース（同じツールで作成） | API 設計書とバックエンドの実装 |

すべてが1つの設計書から作られるので、フロントとバックの食い違いが入り込む場所がなくなります。

| | 内容 |
|---|---|
| メリット | 仕様の置き場所と更新の手順が決まるので、ズレが起きにくく、起きても早く見つかる |
| デメリット | 仕様を先に書く手間が増える。運用フローに慣れるまでチームに負担がかかる |
| デメリットへの対処 | 設計書・実行テスト・テストケースを同じツールにまとめ、作業が二重にならないようにする。自動生成で手作業を減らす |

選ばなかった選択肢は次の2つです。

- **ツールだけ入れる**：更新の手順と担当が決まっていないと、使われなくなる
- **ドキュメントを手で書いて共有する**：実装との同期が手作業になり、すぐに古くなる

## 現場での実践と結果

### RAGチャットSaaSプラットフォーム（12名規模）

- API 仕様が口頭やチャットで管理され、「最新の仕様がどこにあるか分からない」「フロントとバックで認識がずれる」が日常的に起きていた
- API 管理ツール「ApiDog」の導入を提案し、API 設計書の管理・実行テスト・テストケース作成を一元化する運用フローもセットで作った
- フロント・バック間の仕様ズレが減り、結合時の手戻りも減った

| 項目 | 導入前 | 導入後 |
|---|---|---|
| 最新の仕様 | 口頭やチャットに散らばり、どこにあるか分からない | 設計書を見れば分かる |
| フロントとバックの認識 | 日常的にずれる | 同じ設計書をもとに実装する |
| 食い違いが見つかる時点 | 結合の段階で見つかり、手戻りになる | 設計書と実行テストの段階で気づける |

### マーケティングデータ分析プラットフォーム

- Orval で OpenAPI 仕様から API クライアントを自動生成し、React Query と組み合わせて、仕様と実装のズレが起きにくい構成にした

## 現場に合わせた調整

- **すでに OpenAPI などで仕様が書かれている現場**：新しいツールは入れず、仕様からのコード自動生成を足すところから始める
- **少人数でフロント・バックを同じ人が書く現場**：重い運用フローは入れず、仕様の置き場所を一つに決めるだけにする
- **チームが大きく、関係者が多い現場**：仕様の確定と変更の担当を明確にし、変更時の通知の流れまで決める

どの場合も、ツールを押し付けるのではなく、チームの今のやり方から無理なく移れる形を議論して決めます。
